# CI/CD & Release Guide — MealaweUserAppRN

How this app gets built, versioned, and shipped to the Play Store (and later the
App Store) via **EAS Build/Submit + GitHub Actions**. Read this before touching
`eas.json`, `.github/workflows/eas-release.yml`, or cutting a release.

**Scope today: Android fully wired; iOS builds work, submission is partially wired.**
Apple Developer Program enrollment is done, the bundle ID (`com.mealawe.app`) is
registered, and EAS holds a Distribution Certificate + Ad Hoc Provisioning Profile —
`npm run build:prod-preview:ios` / `build:prod:ios` work today. Still outstanding before
`eas submit`/CI can publish iOS builds: an App Store Connect app record, an App Store
Connect API key, and fixing the Push Notifications capability sync (see §8 for all three).

## 1. The pipeline at a glance

```
 developer            GitHub                    EAS (cloud)              Google Play
 ─────────           ────────                   ───────────              ───────────
 git push   ──▶  push to master  ──▶  eas build --profile production ──▶  (AAB artifact)
 git tag    ──▶  push tag v1.2.3 ──▶  eas build --profile production ──▶  (AAB artifact)
                        │                                │
                        ▼                                ▼
              GitHub Actions workflow          eas submit --profile <track>
              (.github/workflows/                        │
               eas-release.yml)                           ▼
                                                Internal / Closed(alpha) /
                                                Open(beta) / Production track
```

- **You never build locally for release.** `eas build` compiles the native
  Android project in Expo's cloud (no Android Studio needed on your machine),
  signs it with the keystore EAS manages remotely, and produces a versioned
  `.aab`.
- **You never touch a keystore file.** Since `android/` is git-ignored and
  regenerated by Expo (`expo prebuild`), signing credentials live only in EAS's
  encrypted credential store, not in this repo or on the CI runner.
- **GitHub Actions is just the trigger + orchestrator.** The actual compile and
  upload happen on Expo's infrastructure; the GitHub runner only calls the
  `eas` CLI and waits.

> **⚠️ `com.mealawe.app` is not a new app.** It's already live on the Play
> Store as "Mealawe: Home Food Delivery" (the existing Ionic app). This RN app
> ships as an **update to that same listing** — which means:
> - Don't create a new app in Play Console. Use the existing one.
> - Builds must be signed with the **original upload keystore**, not a fresh
>   one EAS generates for you. See §4.2 step 5 — import the existing `.jks`
>   into EAS credentials rather than letting it generate a new keystore.
> - The "first release must be uploaded manually" Play Developer API
>   restriction (§4.2 step 3) doesn't apply here — the app has prior published
>   releases already, so `eas submit` should work via the API from the start.

## 2. Versioning strategy (how modern apps do it)

Two numbers move independently, the way every major app (Instagram, Zomato,
etc.) does it:

| Field | Example | Meaning | Who bumps it |
|---|---|---|---|
| **Version name** (`app.json` → `expo.version`) | `1.4.0` | Human-facing, [SemVer](https://semver.org/) `MAJOR.MINOR.PATCH` | You, by hand, per release |
| **Version code** (Android `versionCode`) | `47` | Opaque integer, must strictly increase with every artifact Google accepts | **EAS, automatically** |

### 2.1 SemVer for the version name

- **PATCH** (`1.4.0` → `1.4.1`) — bug fixes, copy tweaks, no new user-facing behavior.
- **MINOR** (`1.4.1` → `1.5.0`) — new feature, backward compatible.
- **MAJOR** (`1.5.0` → `2.0.0`) — breaking change / redesign / dropped backward compatibility (e.g. old app builds can no longer talk to the API).

Bump it in `app.json`:

```json
{ "expo": { "version": "1.5.0" } }
```

Nothing else needs to change by hand — see 2.2.

### 2.2 Version code — fully automatic, don't touch it

`eas.json` already has:

```json
"cli": { "appVersionSource": "remote" },
"build": { "production": { "autoIncrement": true } }
```

This means **EAS's servers**, not this repo, own the Android `versionCode`
counter per build profile. Every `eas build --profile production` bumps it by
one, regardless of what `app.json`'s `version` says. This is the modern,
correct way to do it — you literally cannot forget to bump it or collide with
a previous upload, which is the #1 cause of rejected Play Console uploads.

You can inspect/reset the counter with `eas build:version:get` /
`eas build:version:set` if it ever needs manual correction, but normally you
never run those.

### 2.3 `runtimeVersion` (OTA update compatibility)

```json
"runtimeVersion": { "policy": "appVersion" }
```

This ties [EAS Update](https://docs.expo.dev/eas-update/introduction/)
(JS-only OTA pushes) compatibility to the version name: an OTA update built
against `1.5.0` will only be offered to installed `1.5.0` binaries. Bumping
the version name (2.1) is therefore also how you "cut" a new native-compatible
update channel — keep this in mind, a PATCH bump still creates a new runtime
version boundary under this policy.

### 2.4 Git tags + CHANGELOG

- Tag every release commit `v<version-name>`, e.g. `v1.5.0` — matches the
  `app.json` version exactly, no `v` inside the JSON itself.
- The release workflow (§4) treats a `v*.*.*` tag push as "this is an
  intentional release candidate" and auto-submits it to the **alpha** (closed
  testing) track — see §3.
- Keep [CHANGELOG.md](../CHANGELOG.md) up to date ([Keep a
  Changelog](https://keepachangelog.com/en/1.1.0/) format) — move the
  `[Unreleased]` section's entries under a new `## [1.5.0] - YYYY-MM-DD`
  heading as part of the same commit you tag.

### 2.5 Release runbook (copy/paste)

```bash
# 1. Bump the version name
#    edit app.json: "version": "1.5.0"

# 2. Move CHANGELOG [Unreleased] entries under ## [1.5.0] - 2026-08-17

git add app.json CHANGELOG.md
git commit -m "chore: release 1.5.0"
git tag v1.5.0
git push origin master --tags
```

That push triggers the workflow, which builds and submits straight to the
**alpha (closed testing)** track automatically (§4). From there, promote
through beta → production manually once it's validated (§3.5).

### 2.6 OTA update vs. a new binary — which one does a change need?

Two shipping paths exist, and they cost very different amounts of CI time:

| | `eas update` (OTA) | `eas build` (new binary, via §4) |
|---|---|---|
| Ships | JS bundle + assets only | A newly compiled native app |
| Speed | Seconds, no store review | Full native compile (~10–20 min) + Play/App Store rollout |
| Reaches | Installed apps matching the current `runtimeVersion` (2.3) | New installs / anyone who updates |
| Use for | JS/TS logic, styling, copy, most bug fixes — anything that doesn't touch native code | New/updated native module, `app.json` native config, `plugins/*.js`, permissions, native SDK version bumps |

**Rule of thumb:** if the change is entirely inside `src/`, `assets/`, or app-level
config that doesn't touch `android`/`ios`-native behavior, publish it with
`eas update` instead of waiting for/paying for a full `eas build`. Reach for a
new binary only when native code, a config plugin, permissions, or a native
SDK actually changed.

This is also why the workflow (§4.1) ignores docs-only pushes (`docs/**`,
`**.md`, `.vscode/**`, `.maestro/**`) — those can't affect the compiled binary
either way, so there's nothing for `eas build` to do.

### 2.7 Publishing an OTA update

The channels already exist (auto-created by the first `eas build` on each
profile — `staging` and `production`, matching the `channel` field on every
`eas.json` build profile) and the native side is already wired
(`expo-updates` writes its config into the generated `AndroidManifest.xml`
automatically, no manual setup needed). Publishing is a deliberate, manual
action — nothing in CI auto-publishes an update:

```bash
npm run update:staging      # → the staging channel (internal/dev-client builds)
npm run update:production   # → the production channel (the store build)
```

Both run `eas update --branch <channel> --environment <env>`. The
`--environment` flag is required for this project's SDK (57 — EAS requires it
from SDK 55 onward); it selects which EAS server-side environment variable
set to inject at bundle time, not anything about your local shell env. This
project doesn't currently define any EAS environment variables, so the value
matters only for forward-compatibility, not because it changes today's
output.

Leave off `-m "message"` and the CLI prompts for one interactively — same
pattern as every other `eas` script in this file. **An update only reaches
installed apps whose `runtimeVersion` (2.3) matches** — since this project
uses `policy: "appVersion"`, that means only devices already on the exact
`app.json` version you last built and shipped as a binary. Bumping the
version name always creates a new runtime-version boundary, OTA or not.

The app's own update behavior is intentionally the native default: check on
every launch, download in the background, apply on the *next* cold launch —
no in-app "restart now" prompt. Silent and standard; revisit only if a class
of fix genuinely needs to reach users faster than their next natural app
close/reopen.

## 3. Android release tracks, explained

Google Play has four tracks. Map them to the classic "alpha / beta / release"
language like this:

| Play Console name | Classic name | Who sees it | Review | Purpose |
|---|---|---|---|---|
| **Internal testing** | — (fastest inner loop) | Up to 100 testers you add by email, added instantly | **No review**, live in minutes | Smoke-test every merge before anyone else sees it |
| **Closed testing** | **Alpha** | A trusted group you invite via email list, Google Group, or access code. Multiple closed tracks can run in parallel for different feature sets | Light review | Structured pre-release testing with real (but trusted) users |
| **Open testing** | **Beta** | Anyone who opts in publicly from the Play Store listing | Standard review | Public beta — gather feedback/metrics at scale before full launch |
| **Production** | **Release** | Everyone | Standard review | Full public availability |

### 3.1 Internal testing
> *Quickly distribute your app to up to 100 internal testers using email addresses.*

No review, available within minutes of upload. This is where every automatic
build from `master` lands (§4) — the fastest possible feedback loop for the
core team/QA. Set it up once: Play Console → **Testing → Internal testing** →
create a tester email list.

### 3.2 Closed testing ("alpha")
> *Test your app with a larger group of trusted users using email addresses,
> Google Groups, or access codes. You can create multiple closed testing
> tracks to test different features at the same time.*

This is the **alpha** track (`eas submit --profile alpha` submits here — the
Play Developer API's literal track name is still `alpha` even though the UI
renamed it). Every tagged release (`v1.2.3`) lands here automatically. Invite
a wider, still-trusted group: internal stakeholders, external QA vendor,
select power users.

You can create **additional** closed tracks beyond the default (e.g.
"Closed testing (beta features)") from Play Console if you want to test
specific feature flags with different groups in parallel — those extra tracks
need their own submit profile in `eas.json` with a custom `track` value.

### 3.3 Open testing ("beta")
> *Let anyone sign up to test your app publicly on Play to gather early
> feedback from a large number of users, and monitor key metrics before you
> launch.*

This is the **beta** track. Anyone can opt in from a public link on your Play
Store listing (even before the app is otherwise published). Promote here once
alpha testers have signed off — trigger manually via `workflow_dispatch` (§4)
or promote the exact same alpha build from Play Console (recommended, §3.5).

### 3.4 Production ("release")

Full public rollout. `eas.json`'s `production` submit profile defaults to
`rollout: 1` (100% immediate). For a safer staged rollout, change that
submit profile to `"releaseStatus": "inProgress", "rollout": 0.1` and increase
the percentage from Play Console over the following days — standard practice
for major releases.

### 3.5 Promoting without rebuilding (recommended)

The safest release practice is: **the exact binary that passed alpha/beta
testing is the one that reaches production** — not a fresh rebuild. Google
Play supports this natively:

Play Console → **Testing → Closed testing** → find the tested release →
**Promote release** → choose Open testing or Production → roll out.

No new upload, no new `versionCode`, zero risk of "it worked in beta but broke
in the prod build." Prefer this over re-running the workflow with a different
`submit_track` input, which *does* produce a brand new build.

### 3.6 Internal App Sharing — a different thing entirely

Google Play's **Internal App Sharing** is *not* a track and has nothing to do
with the four tracks above:

- Any signed build (APK or AAB, including plain debug/dev-client builds) can
  be uploaded to get an instant shareable link — no Play Console review, no
  track assignment, no tester list, no effect on your app's release history
  or `versionCode` sequencing rules.
- It's the equivalent of "just send me the build" — useful for handing a build
  to a designer, PM, or one-off stakeholder who isn't part of your formal
  tester lists and doesn't need it going through a track at all.
- Upload manually at Play Console → **Internal app sharing**, or via
  `eas build --profile staging` (this repo's ad-hoc/APK profile) and share the
  resulting EAS build link directly — that link installs straight to a device
  without Play Console at all, which is normally simpler than internal app
  sharing for this project since EAS already provides its own instant-install
  links for `distribution: "internal"` builds.

## 4. GitHub Actions setup

### 4.1 Workflow file

[`​.github/workflows/eas-release.yml`](../.github/workflows/eas-release.yml):

| Trigger | Build profile | Submit track | Why |
|---|---|---|---|
| Push to `master` (no tag) | `production` | **internal** | Continuous inner-loop feedback on every merge |
| Push tag `v*.*.*` | `production` | **alpha** (closed) | Deliberate release candidate → trusted testers |
| Manual (`workflow_dispatch`) | your choice | your choice (or `none`) | Push straight to beta/production, or build-only |

**Docs-only pushes don't trigger this workflow at all** — `paths-ignore`
excludes `docs/**`, `**.md`, `.vscode/**`, and `.maestro/**`, since none of
those can affect the compiled binary (see §2.6 for the OTA-vs-binary policy
this is built on). A commit that touches even one file outside that list
still runs the workflow normally.

**Upstream-only.** Both jobs carry `if: github.repository ==
'pratapmealawe/MealaweUserAppReactNative'` — real EAS builds/submits (and the
credits/App Store side effects they cause) only ever run in the canonical
upstream repo, never in a personal fork (e.g. `origin` →
Apurv-Patole/MealaweUserAppReactNative) even if this workflow file exists
there too. `github.repository` reflects whichever repo GitHub Actions is
actually executing in — it has no relationship to local git remote names, so
this is the correct way to express "only from upstream" in CI (a local
`git remote` named `upstream` doesn't by itself change where Actions run).

Run it manually from GitHub: **Actions → EAS Build & Submit → Run workflow**
and pick the profile/track — or via CLI: `gh workflow run eas-release.yml -f
build_profile=production -f submit_track=beta`. This triggers both the
`android-build-and-submit` and `ios-build-and-submit` jobs (§8.6) — the iOS
job only submits for `internal`/`production` tracks and only once its Apple
setup (§8.3) is complete.

### 4.2 One-time setup steps

1. **Create an Expo access token for CI.**
   - Prefer an **organization robot user** over a personal token (Expo →
     `yagy-team` org → Members → add a robot user) — scoped to CI, doesn't
     evaporate if a person's account changes.
   - If a robot user isn't available on your plan: any member can create a
     personal token at [expo.dev/settings/access-tokens](https://expo.dev/settings/access-tokens).
   - Add it to GitHub: repo → **Settings → Secrets and variables → Actions →
     New repository secret** → name it `EXPO_TOKEN`.

2. **Create the Google Play service account** (lets EAS/CI upload without a
   human logging in):
   - Play Console → **Setup → API access** → "Choose a project to link" (or
     create a new Google Cloud project) → **Create new service account** —
     this opens Google Cloud Console with the right project preselected.
   - In Google Cloud Console: **IAM & Admin → Service Accounts → Create
     Service Account** → give it a name like `eas-play-release`.
   - **Keys** tab → **Add key → Create new key → JSON** → download it. This
     file is a secret credential — never commit it (already covered by
     `.gitignore`: `play-store-credentials.json`, `*service-account*.json`).
   - Back in Play Console → **API access**, the new service account should
     appear → **Grant access** → give it at least: *Release manager* permission
     (or, minimally, "Release to production, exclude devices, and use Play
     App Signing" + "Release apps to testing tracks").

3. **First release, for a genuinely new app only.** The Play Developer API
   (which `eas submit` uses) cannot publish the first-ever version of a
   brand-new app — Google requires one manual upload through the Play Console
   web UI before API access is unlocked. **This does not apply to
   `com.mealawe.app`** — it already has published releases from the Ionic
   app, so `eas submit` can publish to any track from the very first CI run.
   (Still fine to do one upload by hand instead if you'd rather see the Play
   Console flow once before automating it — see §9 for that walkthrough.)

4. **Add the service account key as a GitHub secret** (base64-encoded so it
   survives as a single-line secret):
   ```bash
   # macOS/Linux:
   base64 -i play-store-credentials.json -w 0 | pbcopy   # (drop -w 0 on macOS if unsupported)
   # Windows PowerShell:
   [Convert]::ToBase64String([IO.File]::ReadAllBytes("play-store-credentials.json")) | Set-Clipboard
   ```
   Paste as repo secret `PLAY_STORE_SERVICE_ACCOUNT_KEY_BASE64`.

5. **Import the existing Android keystore into EAS** — do **not** let EAS
   generate a new one. `com.mealawe.app` already has a signing identity Google
   Play recognizes; a fresh keystore would make every upload get rejected as
   an unrecognized signer (or worse, look like a different app).
   - First confirm the `.jks` you have is the right one: Play Console → your
     app → **Setup → App integrity** → note the "Upload key certificate"
     SHA-1, then run `keytool -list -v -keystore your.jks -alias YOUR_ALIAS`
     locally and compare fingerprints.
   - Once confirmed:
     ```bash
     npx eas-cli credentials --platform android
     ```
     Pick the `production` build profile → Keystore → the option to
     **upload/use an existing keystore** (not "generate a new keystore") →
     supply the file, keystore password, key alias, and key password when
     prompted. EAS stores it encrypted, tied to this project.
   - CI builds authenticate as the `yagy-team` Expo account (via
     `EXPO_TOKEN`) and pull this exact keystore from EAS automatically — the
     file itself never touches the GitHub runner or this repo.
   - Keep at least one independent backup of the original `.jks` somewhere
     durable (password manager, secure cloud storage) — EAS holds a copy once
     imported, but losing every copy means going through Google's key-reset
     process to recover.

### 4.3 Secrets summary

| Secret | Where it's used | What it is |
|---|---|---|
| `EXPO_TOKEN` | `expo/expo-github-action` step | Auth to Expo/EAS (build + submit, both platforms) |
| `PLAY_STORE_SERVICE_ACCOUNT_KEY_BASE64` | Decoded to `play-store-credentials.json` before `eas submit` (Android) | Auth to Google Play Developer API |
| `APP_STORE_CONNECT_API_KEY_BASE64` | Decoded to `app-store-connect-api-key.p8` before `eas submit` (iOS) | Auth to App Store Connect API — not yet added, see §8.3 |

Nothing Android-signing-related is stored in GitHub — that lives in EAS's
credential store (step 5 above). Same for iOS: the Distribution Certificate +
Provisioning Profile live in EAS's credential store (§8.1); only the App
Store Connect API key needs a GitHub secret, since that's what CI uses to
authenticate the *submission*, not the build.

## 5. `eas.json` reference

### 5.1 Build profiles (what gets compiled)

| Profile | Distribution | Artifact | Use for |
|---|---|---|---|
| `development` | internal (ad-hoc link) | APK, dev client | Local development on a device |
| `staging` | internal (ad-hoc link) | APK | Quick QA / ad-hoc sharing, staging API |
| `production-preview` | internal (ad-hoc link) | APK | Smoke-test a prod-config build before submitting to any track |
| `production` | store | AAB | **The only profile submitted to Play Store tracks** |

### 5.2 Submit profiles (where it's uploaded)

Submit profiles are independent of build profiles — you build once with
`production`, then submit that artifact to whichever track submit profile you
choose:

```bash
eas build --platform android --profile production
eas submit --platform android --profile internal --latest   # or alpha / beta / production
```

`internal` / `alpha` / `beta` / `production` here are the **literal track
names** the Play Developer API expects — that's why the submit profiles in
`eas.json` are named exactly that (see §3 for what each means on Play Store).

## 6. Command cheat sheet

```bash
# Local ad-hoc APK (no store, instant install link)
npx eas-cli build --profile staging --platform android

# Prod-config APK, still ad-hoc (pre-submission smoke test)
npx eas-cli build --profile production-preview --platform android

# The real release artifact (AAB)
npx eas-cli build --profile production --platform android

npx eas-cli submit --profile internal --platform android --latest
npx eas-cli submit --profile alpha --platform android --latest
npx eas-cli submit --profile beta --platform android --latest
npx eas-cli submit --profile production --platform android --latest

# Build + submit in one shot (what CI does)
npx eas-cli build --profile production --platform android --non-interactive --auto-submit --auto-submit-with-profile internal

# Manage the Android keystore
npx eas-cli credentials --platform android

# Manually correct the remote versionCode counter (rare)
npx eas-cli build:version:get --platform android
npx eas-cli build:version:set --platform android
```

### 8.1 Done already

- Bundle ID `com.mealawe.app` registered on the Apple Developer Portal ✅.
- iOS credentials set up via `npx eas-cli credentials --platform ios` → **All**

  Both survive `expo prebuild` since `ios/` is git-ignored and regenerated —
  hand-editing `ios/Podfile` directly would not stick.

### 8.2 Known issue — Push Notifications capability

When EAS registered the bundle ID, syncing the **Push Notifications**
capability onto it failed with an Apple 403:

```
Failed to patch capabilities: [{ capabilityType: 'PUSH_NOTIFICATIONS', option: 'OFF' }, ...]
Apple 403 detected - Access forbidden.
```

This is almost always the Apple Developer account role lacking **Admin** or
**App Manager** (a plain "Developer" role can't modify capabilities via the
API). Since this app ships push via `@react-native-firebase/messaging` +
`UIBackgroundModes: remote-notification` (`app.json`), push will not work on
device until this is fixed:

1. Check the role of the account/API key EAS uses at
   developer.apple.com/account/#/people — needs Admin or App Manager.
2. Or manually enable **Push Notifications** on the bundle ID at
   developer.apple.com/account/resources/identifiers (find `com.mealawe.app`).
3. Re-run `npx eas-cli credentials --platform ios` (or just rebuild)
   afterward — EAS will pick up the capability.

### 8.3 Still needed before `eas submit`/CI can publish iOS

1. **Create the App Store Connect app record** — App Store Connect → My Apps
   → **+** → New App, bundle ID `com.mealawe.app`, matching SKU. Gives you the
   numeric **ASC App ID** (from the app's App Store Connect URL).
2. **Create an App Store Connect API Key** for non-interactive CI submission:
   - App Store Connect → **Users and Access → Integrations → App Store
     Connect API** → **Generate API Key** → role "App Manager".
   - Download the `.p8` key once (Apple only allows this once) — note its
     **Key ID** and **Issuer ID** (shown on the same page).
3. Fill in the placeholders already scaffolded in `eas.json`'s
   `submit.internal.ios` / `submit.production.ios` blocks: `ascAppId`,
   `ascApiKeyId`, `ascApiKeyIssuerId`. These three are identifiers, not
   secrets — safe to commit directly.
4. Create a **TestFlight internal testing group** in App Store Connect (→ the
   app → TestFlight → Internal Testing) and put its exact name into
   `submit.internal.ios.groups` in `eas.json`, replacing the placeholder.
5. For CI: base64-encode the `.p8` file and add it as the GitHub secret
   `APP_STORE_CONNECT_API_KEY_BASE64` (same pattern as
   `PLAY_STORE_SERVICE_ACCOUNT_KEY_BASE64` — see §4.3). The `ios-build-and-submit`
   job in `eas-release.yml` is already wired to decode it; it currently
   **skips** (not fails) because the secret doesn't exist yet.

### 8.4 TestFlight ≈ Android's tracks — where the analogy breaks down

| TestFlight | Android equivalent | Automatable via `eas submit`? |
|---|---|---|
| **Internal testing** (up to 100 App Store Connect users, no review) | Internal testing track | **Yes** — `submit.internal.ios.groups` auto-adds the build to a named internal group |
| **External testing** (up to 10,000 testers via link/groups, "Beta App Review" first time per version) | Closed (alpha) + Open (beta) testing, combined | **No** — `eas submit`'s `groups` field only accepts *internal* group names. Adding a build to an external group is a manual step in App Store Connect after upload |
| **App Store release** | Production track | **Partially** — `eas submit --profile production` uploads the build to App Store Connect, but does not click "Submit for Review"; that final step is manual in App Store Connect |

This is why `eas.json` only defines `submit.internal.ios` and
`submit.production.ios` (not `alpha`/`beta`) — unlike Android, there's no
API-level way to route the same iOS build to different named tracks, so
mirroring all four Android submit profile names on iOS would be misleading.
`ios-build-and-submit` in the workflow reflects this: any `submit_track`
input other than `internal`/`production` just builds without submitting on
iOS, even when the Android job submits to alpha/beta.

### 8.5 iOS versioning

- `app.json` → `expo.version` is shared with Android — one SemVer number for
  both platforms, which is what most cross-platform apps do.
- `CFBundleVersion` (the iOS equivalent of `versionCode`) is handled the same
  way as Android's: `appVersionSource: "remote"` + `autoIncrement: true`
  already covers iOS now that `ios` build profiles exist — EAS keeps a
  separate remote counter per platform automatically (already visible: the
  iOS `buildNumber` has been auto-incrementing across the test builds run
  while wiring this up).

### 8.6 GitHub Actions — `ios-build-and-submit`

Already added to `eas-release.yml` as a second, independent job (same
triggers/inputs as the Android job). It builds iOS on every push the Android
job builds on, and submits when `submit_track` resolves to `internal` or
`production` (see §8.4 for why not alpha/beta) — gated on
`APP_STORE_CONNECT_API_KEY_BASE64` existing so it's inert until §8.3 is done.

## 9. First manual release walkthrough (this app, right now)

This app is **not new** — `com.mealawe.app` is already published as "Mealawe:
Home Food Delivery" (the Ionic app). This section is the concrete, one-time
sequence to get this React Native codebase publishing an update to that same
listing, signed correctly, into Internal testing.

1. **Confirm the keystore you have is the right one.** Play Console → the
   Mealawe app → **Setup → App integrity** → note the "Upload key
   certificate" SHA-1. Then:
   ```bash
   keytool -list -v -keystore /path/to/your-original.jks -alias YOUR_ALIAS
   ```
   Fingerprints must match before you go any further. If they don't, this
   isn't the right file/alias — don't attempt an upload with it.

2. **Import it into EAS** (see §4.2 step 5 above for the full detail):
   ```bash
   npx eas-cli login
   npx eas-cli credentials --platform android
   ```
   → `production` profile → Keystore → **upload/use an existing keystore** →
   provide the file + passwords + alias. Do not choose "generate a new
   keystore."

3. **Build the AAB:**
   ```bash
   npm run build:prod
   ```

4. **Upload to Internal testing** — in the *existing* Play Console app (don't
   create a new one):
   - **Testing → Internal testing** → create a tester email list if there
     isn't one yet.
   - **Create new release** → upload the `.aab` from step 3 → add release
     notes → **Save → Review release → Start rollout to Internal testing**.
   - No Google review; live for testers within minutes. Share the internal
     testing opt-in link from that page.

5. **Once this works, wire up automation** (§4.2 steps 1, 2, 4 — the
   `EXPO_TOKEN` and Play Store service account secrets) so future pushes to
   `master`/tags go through `eas-release.yml` automatically instead of this
   manual upload.
