# Platform-Native Features Implementation Plan — Widgets, Rich Push, Deep Linking, Biometric Auth, Store Review, Background Refresh

**Project:** MealaweUserAppRN (Expo SDK 57 · RN 0.86 · React 19.2 · Expo Router)
**Companion doc:** [`LIVE-ORDER-TRACKING-PLAN.md`](LIVE-ORDER-TRACKING-PLAN.md) already covers iOS Live
Activities/Dynamic Island ("Phase 3" — **shipped** at the JS/config layer, see
`src/features/tracking/liveActivity.tsx` + `useDeliveryLiveActivity.ts`; only push-to-start/update-token
backend work remains) and the Android ongoing tracking notification ("Phase 2" — **already shipped**,
see `src/features/tracking/`). This doc covers the
remaining platform-native items from the Performance/UX/Tooling proposal's Section 8: **home/lock-screen
widgets, rich push actions, deep linking, biometric auth, in-app store review prompts, and background
refresh for order status**. Don't duplicate Phase 3 planning here — reference it.
**Status:** Implemented at the JS/config layer for all six items (Phases A–F) —
`expo-local-authentication`, `expo-store-review`, `expo-background-task`, `expo-widgets`,
and the `app.json` deep-linking config are all installed and wired in. Verified via
`npx tsc --noEmit`, `npx expo export` (Android + iOS bundles), and
`npx expo config --type public` (confirms the `expo-widgets` config plugin correctly
generates the EAS Build iOS extension-target config). **Not verified:** actual native
rendering/behavior on a real device or EAS build — nothing here has run on Xcode,
a physical iOS device, or a from-scratch Android build yet. Backend-side work (APNs
Live Activity pushes, any push-payload fields this doc assumes) is still outstanding
and tracked per-phase below.

## 1. What exists today

- **Push transport:** `@notifee/react-native` + `@react-native-firebase/messaging` are already
  integrated (used by the tracking notification and general push handling in
  `src/services/push/notifications.ts`). Every notification shown today uses a single default
  `pressAction` (opens the app) — no image attachments, no multi-button actions.
- **Routing:** Expo Router (file-based, `src/app/`) already maps URL-shaped paths to screens, and
  `app.json` has a custom scheme (`mealaweuserapprn://`). What's missing for real deep linking is the
  domain-verification layer (Universal Links/App Links), not the routing logic.
- **Session/security:** `expo-secure-store` holds the auth session; `react-native-mmkv` holds
  lighter-weight local state. Nothing biometric-gated exists.
- **Native project:** managed/CNG — `android/` and `ios/` are git-ignored, regenerated by
  `expo prebuild`. Any new native surface needs a config plugin so it survives every prebuild, same
  constraint `LIVE-ORDER-TRACKING-PLAN.md` documents for Phase 3.
- **Order status refresh today is entirely push-driven:** the FCM data-message handler in
  `src/features/tracking/` is the only thing that updates order state when the app isn't foregrounded —
  there's no OS-level scheduled background task as a fallback if a push is delayed or dropped (which
  happens; neither FCM nor APNs guarantees delivery).
- **Nothing exists yet** for widgets (either platform), rich/actionable push, associated domains,
  biometric auth, in-app store review prompts, or scheduled background refresh.

## 2. Phased plan

### Phase A — Home/Lock Screen Widgets (proposal priority: NOW / launch)

A widget for "your current order" or "reorder your usual" — a zero-tap way back into the app from the
home screen (iOS) or lock screen (iOS 16+). This is a **standalone gap**, not covered by the live-tracking
plan, though it shares infrastructure with it on iOS.

**Recommended v1 scope:** "reorder your usual" (relatively static, refreshes on a schedule) rather than a
live order-status widget — the latter duplicates what the Live Activity (iOS) and ongoing notification
(Android) already do once Phase 3 ships, for meaningfully more native complexity. Revisit a live-status
widget only if user research specifically asks for it outside the Lock Screen/notification surfaces.

| Platform | Approach |
|---|---|
| iOS (WidgetKit) | **Implemented** via `expo-widgets` (`src/features/orders/orderWidget.tsx`) — the same first-party package used for Phase 3's Live Activity, sharing its config plugin/extension-target infrastructure. Layout is JSX (`@expo/ui/swift-ui` primitives), not hand-written Swift. |
| Android (App Widgets) | Also `expo-widgets`, via its **experimental** `enableAndroid` config flag (currently on in `app.json`) — one shared implementation instead of a second `react-native-android-widget` integration. If this experimental path proves unstable, `react-native-android-widget` remains the documented fallback. |

**Data flow (the part that's easy to underestimate):** a widget runs in a separate process from the app
and can't just read from Zustand/React state. `expo-widgets`' `Widget.updateSnapshot(props)` handles this —
call it whenever the underlying data changes (implemented in `useOrders.ts`, updating the widget with the
most recent delivered order on every load) and the module handles getting that snapshot to the native
widget on both platforms; no manual App Group/UserDefaults plumbing needed at the app-code level (the
config plugin still sets up the App Group for you, since the native widget process still needs it
internally).

<div class="recommend">

**Recommendation:** Sequence right after — or alongside — Phase 3 of the live-tracking plan on iOS (reuses
its extension-target groundwork instead of standing up a second one from scratch); build independently on
Android since the community package keeps that side mostly a JS task. **NOW** (launch-priority, per the
proposal).

</div>

### Phase B — Rich Push Notifications with Actions (proposal priority: NOW · post-launch)

Extends the existing Notifee + FCM integration. Split this into two independently-shippable pieces —
they have very different native cost:

**B1. Action buttons (ship first — low native cost):**
- Android: already fully reachable from the existing Notifee setup — `actions: [{ title, pressAction: { id } }]`
  (up to 3 buttons), handled via `notifee.onForegroundEvent`/`onBackgroundEvent` with
  `EventType.ACTION_PRESS`. "Call rider" → `Linking.openURL('tel:...')`; "Reorder" → hit the reorder
  endpoint directly from the handler or deep-link into the right screen (ties into Phase C).
- iOS: notification actions/categories (`UNNotificationCategory` + `UNNotificationAction`) are
  registerable from JS (Notifee's iOS category API) **without a native extension** — this is the
  cheapest possible win on iOS.

**B2. Image attachments (fast-follow — needs one small native extension):**
- iOS only needs native code for this part: a **Notification Service Extension**
  (`UNNotificationServiceExtension` subclass) that intercepts the incoming push, downloads the image
  URL, and attaches it via `UNNotificationAttachment` before display. Small Swift class, no SwiftUI —
  meaningfully less native surface than a Widget/Live Activity extension, but still needs a config
  plugin to inject the extension target.
- Android already supports this today via Notifee's `AndroidStyle.BigPictureStyle` — no new native
  work.

<div class="recommend">

**Recommendation:** Ship B1 (actions, both platforms) first — no new native extension target required at
all. Follow with B2 (iOS image attachments) once there's a concrete use case (promo banner, order photo)
that justifies the extension. **NOW · post-launch**, B1 before B2.

</div>

### Phase C — Deep Linking: Universal Links / App Links (proposal priority: NOW · post-launch)

The routing logic is largely done (Expo Router). What's missing is upgrading from a custom scheme
(`mealaweuserapprn://`, only works from inside another app that already knows the scheme) to links that
work from anywhere — SMS, WhatsApp, email, search results — without an "open in browser?" prompt.

| Requirement | iOS | Android |
|---|---|---|
| Domain verification file | `apple-app-site-association` at `https://mealawe.com/.well-known/apple-app-site-association` — no file extension, `application/json` content-type, no redirects | `assetlinks.json` at `https://mealawe.com/.well-known/assetlinks.json`, referencing the app's SHA-256 signing certificate fingerprint |
| `app.json` config | `ios.associatedDomains: ["applinks:mealawe.com"]` | `android.intentFilters` entry with `autoVerify: true`, matching `data: { scheme: "https", host: "mealawe.com" }`, categories `BROWSABLE`/`DEFAULT`/`VIEW` |
| Owner of the actual blocker | Web/infra team hosting the association file on the marketing site's domain — **this is the real dependency**, not app code | Same, plus the Android signing certificate fingerprint from Play Console → **Setup → App integrity** (the same page referenced in `docs/CI-CD-RELEASE-GUIDE.md` for keystore verification) |

Once the native config + hosted files are in place, Expo Router picks up incoming Universal Links/App
Links the same way it already handles the custom scheme — no separate JS linking code needed, as long as
the marketing URLs' path structure matches (or is mapped to) the app's route structure (e.g.
`https://mealawe.com/order/123` → `src/app/order-detail.tsx`).

<div class="recommend">

**Recommendation:** This is mostly a coordination task, not an engineering-heavy one — get the two
association files scheduled with whoever owns `mealawe.com`'s hosting early, since that's the actual
critical path, not the `app.json` change. Useful immediately for the in-progress refer-and-earn flow,
marketing campaigns, and notification deep links (ties into Phase B's action buttons). **NOW · post-launch.**

</div>

### Phase D — Biometric Authentication (proposal priority: NOW · post-launch)

The lowest-effort item in this entire plan. `expo-local-authentication` is a first-party Expo SDK module
wrapping Face ID, Touch ID, and Android `BiometricPrompt` behind one JS API
(`hasHardwareAsync`/`isEnrolledAsync`/`authenticateAsync`). No config plugin, no custom native code beyond
adding `NSFaceIDUsageDescription` to `app.json`'s `ios.infoPlist` — it works out of the box under CNG.

**UX decision needed before implementation** (this is a product call, not a technical one):
- Gate app reopen (skip re-entering OTP every session)?
- Gate specific sensitive screens (wallet, saved payment methods)?
- Both, behind an opt-in toggle in Profile/Settings (recommended default: **off**, user opts in — the
  pattern most apps, including banking apps, use, and it avoids surprising anyone)?

The opt-in preference itself is fine to store in `react-native-mmkv` (not sensitive); the actual session
token stays in `expo-secure-store` exactly as today — biometric auth gates *access* to the already-stored
session, it doesn't replace how the session itself is stored.

<div class="recommend">

**Recommendation:** Given how little native lift this needs relative to everything else in Section 8,
it's a reasonable candidate to pull into the launch scope if there's spare capacity — but the safe default
is scheduling it for the first post-launch release alongside Phases B and C. **NOW · post-launch.**

</div>

### Phase E — In-App Store Review Prompts (proposal priority: NOW · post-launch)

Asking for a rating at the right moment (right after a successful delivery, not on app launch) is one of
the cheapest, lowest-risk items in this whole plan — one first-party package, no config plugin, no native
extension.

**`expo-store-review`** wraps both platforms' native APIs behind one call:
- **iOS:** `SKStoreReviewController.requestReview` — Apple caps this at **3 prompts per 365-day period**
  per user and reserves the right to silently not show anything at all; the app cannot detect whether it
  actually displayed. You control *when you call it*, not whether it appears.
- **Android:** Google Play's **In-App Review API** — same idea, a Play-controlled bottom sheet, similar
  quota behavior decided by Play Services, not the app.

**Policy constraint that shapes the trigger design (both stores):** neither Apple nor Google allow gating
the prompt behind your own "are you happy?" pre-filter that only shows it to users who say yes and routes
unhappy users elsewhere — that's explicitly against both stores' review guidelines, not just a style
choice. The prompt has to fire based on **behavioral** signals (e.g., a successful order/delivery, N
completed orders), not sentiment you collected first.

**Recommended trigger logic:**
- Fire only after a genuinely positive moment — order delivered successfully — never right after an
  error or a support interaction.
- Don't ask on the very first order; wait for the 2nd–3rd successful delivery so the prompt reflects
  actual repeat usage.
- Track `lastPromptedAt` + a completed-order counter locally (`react-native-mmkv`, matching how the
  biometric opt-in preference is stored in Phase D) and apply your own cooldown (e.g., don't re-trigger
  for several months) — this is a courtesy on top of the OS's own quota, not a replacement for it.
- Also expose a manual "Rate Mealawe" entry in Settings/Profile that opens the store listing directly via
  `expo-store-review`'s `storeUrl()` + `Linking` — a fallback for users who want to review without hitting
  the OS's own quota-gated prompt, and the only option once the quota's exhausted.

**Shipped:** implemented in `src/features/reviews/storeReviewPrompt.ts`, but the trigger point is
**order placed successfully** (`noteOrderPlacedAsync`, called from `order-result.tsx` on `status ===
'success'`), not order delivered — a deliberate product call made after this proposal, trading the
"wait for the positive delivery moment" reasoning above for reacting to the checkout success moment
instead. Min-count (3) + cooldown (120 days) throttle and the manual "Rate Mealawe" Profile entry are
unchanged from this recommendation.

<div class="recommend">

**Recommendation:** One of the easiest wins in Section 8 — no dependency on anything else in this plan.
Ship alongside Phases C/D/F. **NOW · post-launch** (cheap enough to pull into launch scope if there's spare
capacity, same note as Phase D).

</div>

### Phase F — Background Refresh for Order Status (proposal priority: NOW · post-launch)

Today, anything that updates while the app isn't open (the Phase 2 ongoing notification, and eventually
the Phase 3 Live Activity) relies entirely on a push arriving. Push delivery isn't guaranteed on either
platform — this phase adds an OS-scheduled background task as a resilience fallback, and is also what
would feed a widget's data (Phase A) if a future live-status widget is ever built, since a widget's
`TimelineProvider`/update call needs *something* to populate it even when the app hasn't been opened in a
while.

**`expo-background-task`** (Expo's current, non-deprecated background-task module — successor to the
retired `expo-background-fetch`) wraps both platforms' native scheduling behind one API:
- **iOS:** `BGTaskScheduler`/`BGAppRefreshTask` — the OS decides actual execution timing based on device
  usage patterns and battery state; it is a **budgeted, best-effort** mechanism, not a guaranteed interval,
  and can go a long time between runs if the OS decides not to grant background time.
- **Android:** WorkManager-based periodic work — generally more reliable/frequent than iOS, though Doze
  mode and battery optimization still apply and can delay it.

**Task logic (same on both platforms via one JS task registered with `TaskManager.defineTask`):** on each
background wake, check for any locally-cached active order, call the existing order-status endpoint
(`fetchFoodOrder`, already used by Phase 1 of the live-tracking plan), and if status changed:
1. Update local cache so the next app open shows fresh data instantly.
2. Update the shared App Group data widgets would read from (if Phase A ships a live-status widget later).
3. Optionally reconcile the ongoing Android notification / Live Activity content state locally, as a
   fallback for a dropped push — not a replacement for the push path, a safety net under it.

<div class="recommend">

**Recommendation:** Frame this explicitly as a **resilience and widget-data-feed supplement** to the
existing push-driven updates, not a replacement — neither platform's background scheduling is reliable
enough to be the primary mechanism. Worth having regardless of whether a live-status widget ever ships,
since dropped pushes are a real (if infrequent) failure mode today. **NOW · post-launch.**

</div>

## 4. Testing & rollout notes

Per `docs/TESTING-WORKFLOW.md`'s convention — every feature needs a Maestro flow or an explicit `# MANUAL`
marker with a reason:

- **Deep linking (Phase C)** is fully Maestro-automatable — Maestro supports launching with a link
  directly. This should get a real `.maestro/flows/deep-link-*.yaml`, not a manual marker.
- **Rich push actions (Phase B)** — Maestro can assert on in-app state after a simulated notification tap
  in some setups, but exercising the actual OS notification tray/action buttons is flaky/limited across
  both platforms; plan for a manual QA checklist for the actual tray interaction, with Maestro covering
  what happens in-app once a deep-link-style action fires.
- **Widgets (Phase A)** — home-screen/lock-screen widgets are system UI outside the app's own view
  hierarchy; Maestro cannot drive them. Manual, device-based QA only.
- **Biometric auth (Phase D)** — Maestro cannot interact with the real OS biometric prompt (secure system
  UI, isolated from app automation), the same limitation `TESTING-WORKFLOW.md` already notes for
  OTP-gated flows. Needs a test-only bypass (an env-gated flag skipping the biometric check in CI/test
  builds) to get any automated coverage at all; mark `# MANUAL` until that bypass exists.
- **Store review prompts (Phase E)** — the OS review dialog is system UI Maestro can't drive, and calling
  it repeatedly in test runs risks burning the account's real quota against the App Store/Play Store.
  Test the *trigger logic* (does the app decide to call `requestReview()` at the right moment) via a
  mocked/stubbed version of `expo-store-review` in test builds, not the real dialog. Mark `# MANUAL` for
  the actual native dialog appearance.
- **Background refresh (Phase F)** — OS background scheduling can't be reliably triggered on demand from
  a Maestro flow. Verify the *task logic* (the JS function registered with `TaskManager.defineTask`) with
  a manual invocation path during development, and rely on manual device testing (leave the app backgrounded,
  confirm data refreshed on reopen) rather than an automated flow; mark `# MANUAL`.

All six items need a dev-client rebuild (`expo prebuild` → reinstall) the moment any native
extension/config-plugin work lands — same constraint the other plan document calls out for its Phases 2–3.
Phases E and F don't need a config plugin, so they're the two exceptions that can be added to an existing
dev-client build without a full extension-target rebuild.

   duplicates Live Activity/ongoing-notification coverage for materially more complexity.
2. **Rich push B1/B2 split:** confirm shipping action buttons first (near-zero native cost) separately
   from image attachments (needs the Notification Service Extension), rather than bundling both.
3. **Deep linking ownership:** confirm who on web/infra owns hosting `apple-app-site-association` and
   `assetlinks.json` on `mealawe.com`, and get that scheduled — it's the actual critical path for Phase C,
   not anything in this repo.
4. **Biometric auth scope:** gate app reopen, sensitive screens, or both — a product decision needed
   before implementation starts (Phase D).
5. **Sequencing vs. Phase 3 (Live Activities):** confirm whether widgets (Phase A) should wait for the
   Widget Extension groundwork from the other plan's Phase 3, or stand up its own extension first if
   Phase 3 isn't scheduled yet.
6. **Store review trigger threshold (Phase E):** confirm "after the 2nd–3rd successful delivery" as the
   first-prompt rule, or specify a different order count/cooldown period.
7. **Background refresh scope (Phase F):** confirm this is scoped to active-order status only (as written
   above) rather than a broader "keep everything fresh in the background" mandate (wallet balance,
   subscription status, etc.) — a wider scope changes the task's data-fetch surface significantly.
